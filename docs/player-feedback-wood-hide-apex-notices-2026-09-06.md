## 1. Wood should read as wood from this world

**Accepted:** most wood comes from actual trees coloured by the world's colours. The exact tree wood colour follows the resulting Logs, shaped Hafts and their gear regions. Fallen logs are a permitted supporting source before a good Axe; standing still beside a large tree should not be the only early option.

**Current source distinction:** `Resources.timber` still has the public name “Timber”, while the new physical registry already distinguishes `flora.log.softwood` and `flora.log.hardwood`. Engineering confirms the early source-colour owner supports only Stem/Leaf/Tall Stem foliage. There is no existing wood-channel mapping: the new, Design-authored mapping below must be implemented before new producers claim world-coloured wood. Existing immutable visual receipts provide provenance, not an already resolved wood colour.

Use **Logs** as the common player-facing word, with **Softwood Logs** and **Hardwood Logs** when known. Rename the old “Timber” display term across harvest narration, stock, recipe requirements and choices; retain its stable legacy resource ID, quantity, price and lawful uses. If old type is unknown, show “Logs” with a legacy/unknown-type detail rather than inventing Softwood or Hardwood. The historical term may appear once in explanatory migration text, not as a competing new resource.

Existing untyped Timber that is genuinely wood may satisfy an **any-Log** requirement through the explicit legacy-stock adapter, preserving its real owner/unknown appearance. This includes early Axe/Pick raw-material improvements and appropriate foundations. It must not pass a Hardwood-only bow/Haft requirement by name alone or be copied into both typed stocks. No stock deletion, automatic packing, new Axe gate or free improved tool. Starting Axe1 and small-tree routes remain valid; explain smaller trees/fallen wood when a standing tree needs a better Axe.

For opted-in tree production, freeze the actual rules-owned wood base colour from the world's resolved palette/source assignment at generation, and use that same source value for the visible woody tree region and its harvested material. Keep leaf/lighting/shading treatment distinct from inherent wood colour. Do not sample screenshots, choose a nearby species or recolour a saved Log from the current world. Explicit saved source colour stays exact through harvest, Return, stack selection, Haft preparation, gear construction/refit and recovery. Missing historical colour remains unknown; known source colour does not become unknown merely because final art mapping is pending.

Fallen wood must be an explicit finite loose-log source, not a phantom standing tree or a new universal wood generator. Keep existing lawful placement budgets, reserved source promises and finite yields; no new global spawn quota or guarantee is implied. If a new typed adapter is needed, use the actual source's known wood type/colour, not a guessed Hardwood reward. Gather through its existing underfoot/low-tool action, with no newly imposed high-Axe gate. Do not backfill arbitrary new sources into saved worlds. Standing trees remain the primary route.

### Wood colour mapping · complete Design-authored first pass

This closes the specific mapping dependency reported by Engineering on delivered source `44f86f3872d30ee022e20414b05d72cba692205f` / delivery `0bde0365286198aa19f7d6da603d3147e409ad75`. It is implementation-ready first-pass tuning, not a newly attributed personal Aimee decision. No new ink, writing Focus, research, material quality or resource abundance is introduced.

**Authority and scope.** Add a versioned physical source colour with semantic channel **wood**, policy `early-wood-colour-1.0.0`, beside the existing foliage receipt. Do not relabel `EarlyPlantColour` as wood or add trees to its foliage producer set. Reuse the immutable `EarlyMaterialSourceReceipt.visualReceipt` and actual source/harvest ownership. This is a derived flora material channel, not a fifth player-authored `WorldVisualScope`: existing Bloom → `floraTendency` remains the only writing input relevant here. Granite/material, Sun/emitter and Smoke/atmosphere cannot supply inherent wood colour. Generic specimen `FloraTraits.coloration` is not an implicit wood assignment.

Resolve at generation, in this order:

1. A valid explicit **wood** assignment for this actual source identity wins. It must carry the source identity, immutable world visual receipt identity, exact three integer sRGB channels in 0…255, and its assignment identity. An existing authoritative saved wood colour is retained exactly; no new transformation applies to old known colour.
2. Otherwise use `visualReceipt.request.resolvedColors.floraTendency.srgb`, when present and valid, as the exact wood base. This explicitly extends the existing flora palette tendency into a woody material consumer. It reads the saved rules-owned palette input, not leaf pixels, the foliage receipt, a rendered crown, or current illumination. The first pass adds no brown cast, lightness shift or per-tree jitter to authored colour.
3. With no authored flora tendency, generate and freeze a wood palette entry per actual woody species in this world. If this producer has no species identity, use its stable physical producer family (`smallSoftwood` or `smallHardwood`), not a guessed adjacent species. Seed from the immutable world seed plus a distinct wood-policy namespace and that stable species/family identity; never use process-random hashing, source allocation order, coordinates, the foliage RNG stream or frame time. Engineering may use the existing deterministic seed derivation, recording the encoding with this version. Draw hue uniformly from integer 0…359; choose saturation band with weights 20% / 50% / 30%, then draw saturation uniformly from respectively 0…12 / 25…55 / 60…85%; draw lightness uniformly from 35…65%. Resolve via the existing `WorldGrade2V1.resolvedSRGB` conversion and persist the exact integer result. This is an open colour range, not a brown-only palette. Reuse the frozen species/family entry for matching sources; no specimen jitter in this first pass.

A malformed explicit assignment or present-but-invalid palette is a validation failure, not permission to silently fall through to random colour. Record the chosen basis (explicit source / resolved flora tendency / generated wood species or family), policy version, relevant identity and immutable world visual receipt reference with the source's exact sRGB. The source must own the colour before harvest; generated colour is never resolved for the first time by a renderer or inventory screen.

**Exact visible consumer.** In `Sources/Screens/OrthographicWorldPrototypeView.swift`, `loadTree()` currently imports `orthographic-tree-v1.usdz` with authored materials. Its editable source `AssetLab/source/orthographic-prototype-v1/create_tree.py` defines object `stem` with material `prototype stem — neutral`, separate from `crown` / `prototype crown — neutral`. The **stem's woody material region** consumes the actual represented source's frozen wood sRGB as inherent base colour. Replace the neutral base tint; multiplying the receipt by the old brown tint would change the promised colour. Preserve geometric shading, shadows and existing fading. Crown stays under its existing foliage rules. Require an explicit exported/imported region binding; do not identify wood by brown pixels or tint the entire entity. If import changes names, Engineering binds the verified equivalent stem region before claiming delivery. This does not authorize new artwork or an Asset revision.

A display-only tree without an actual wood-source binding must not borrow the nearest gatherable node's colour. Connect the actual tree/source owner before claiming the tree → Log path. For any existing enabled standing, small-tree or finite fallen-log producer, the visible woody region and harvested lot read the same source receipt. A fallen piece with a recorded parent inherits that parent's wood colour; an independently generated loose-log source follows its own known species/family assignment. No inferred parent, invented species or extra spawns. Future branch, cut-end and loose-log models must bind their woody regions to the same material receipt when those consumers exist; they are not speculative Asset work now.

**Save boundary.** Opt in only worlds and wood sources generated under the new policy. Preserve old `WorldVisualReceipt` bytes/hashes and existing foliage receipts; no rewriting the old four-scope schema or regenerating a saved world to add wood colour. Previously saved sources/stock with known authoritative wood colour retain it. Missing historical wood colour stays unknown even if that old world has a flora palette: do not retroactively assign it. Old visuals may retain their existing appearance, without making it a material provenance claim. Missing wood in a new-policy source is an incomplete generation/validation result to resolve before enabling that source, not a guessed legacy fallback. Remembered trees preserve their last-observed appearance and reveal no hidden source updates.

**Downstream consistency.** Harvested Logs retain the same actual source colour through Return, stock grouping, trade, Hafts, active equipment components, refit and recovery. Several differently coloured inputs keep their individual regions/constituents; no averaging into a fabricated source shade. Wood colour changes no hardness, Softwood/Hardwood identity, item stats, price or yield.

Use the normal bounded Engineering implementation checks: explicit-source precedence; a saved flora tendency reaching the stem and its exact harvested lot; deterministic nil-tendency generation shared within the actual species/family; unchanged crown and remembered-tree disclosure; and old known/unknown stock surviving without recolour. Include downstream material preservation in the existing source → craft route. Design does not repeat native or phone checks.

### Flora drops and crafting colour · direct Aimee clarification, 6 September

**Accepted intended behavior:** flora follows the same source-to-material continuity as wood. Every harvested flora part retains its actual part/source colour and Pattern, where defined, for use in crafting. This is visible material appearance, not merely genealogy hidden in a receipt. The full journey is source part → harvested lot → Return/stock → selected prepared constituent → finished component → refit/recovery. No claim of complete current delivery is made by this clarification.

Use the actual part's frozen rules-owned appearance when one exists, retaining the parent species/source and any part-specific assignment. Do not replace a known stem, leaf, root, bark, sap or spore colour with a convenient whole-plant, nearby plant or current-world colour. Existing supported Stem/Leaf/Tall Stem receipts remain valid and exact; no reroll or blanket migration. For a new named-part producer without a part-specific appearance, its production mapping must explicitly record whether it inherits the generated parent flora palette or has its own resolved part colour before harvesting is enabled. This names an implementation dependency for those producers, not permission to sample a rendered crown or invent anatomy. Saved unknown appearance remains unknown; a known non-RGB colour/Pattern must be preserved even when final RGB/art mapping is still pending.

Prepared structural flora materials retain the selected colours as their actual appearance. In particular, two Fibre become Cord with those two source-coloured strands; four Fibre become Cloth with those four source-coloured sections. Pulp retains the appearance of its actual constituent source under its one-to-one unit allocation. Equipment bindings, woven panels and other visible flora-derived regions consume those same component appearances. Mixed sources remain allowed: preserve their ordered constituents, let the player choose relevant sources in the quote, and never flatten them into an invented average colour or discard differences under a broad stock heading. A single type stack may retain exact selectable underlying lots; choosing one must consume that lot, not an arbitrary differently coloured equivalent. Refit/recovery retains the actual surviving prepared component, with no duplicate raw ancestors.

Ungraded means no creature-quality band; it does not mean neutral-coloured or colourless. Appearance itself adds no stats, potency, value or extra ingredient requirement. Existing explicitly transformed outputs keep their recipe-owned rules: standardized remedies retain recognizable bottle colours, and named extracted pigments/CMY+Depth ink retain their authored pigment identities. Their actual flora input appearance still remains in provenance, but a coloured leaf is not automatically a dye ingredient. This does not create a dyeing system or change a preparation's effect.

This clarification governs every relevant shop contract. The ordinary Engineering check should follow one genuinely coloured flora source through harvest, a chosen Cord/Cloth constituent and the corresponding visible equipment region, then reopening/recovery; include a mixed-colour choice retaining both actual sources. Extend the existing material route rather than creating a separate audit or a Design phone check. A newly enabled named part must carry its own declared appearance mapping through the same route.

## 2. Equivalent Hide should appear as a stack

**Accepted:** equivalent covering materials visibly group on Return, in Storehouse and in material selectors, with a quantity instead of repeated identical rows. The actual underlying source ownership remains intact.

A typed equivalence group uses exact material subtype, quality band, full source colour/Pattern and all recipe-relevant physical facts: coverage, hardness, covering length, flexibility and coveringProtection under the current Hide/Leather contract. Keep unsupported legacy families separate. World/creature/source IDs and genealogy are retained underneath, but do not split otherwise equivalent physical results into separate visible rows. Different genuine properties/bands/colours remain distinct; do not average them or broaden recipe eligibility.

A group is a display/selection aggregation, not destruction or merging of owned source receipts. Returning three equivalent portions from different specimens shows one row ×3. Selecting two allocates two real units once in stable inventory order, with source detail available when requested. Reload/refusal/stale quotes retain all quantities. Return's gathered/lost/kept categories remain separate if their outcome differs.

Old/new nominal price policies do not create fake material types. Quotes sum the actual selected lot prices; a visible physical group with different historic prices must not pretend all units share one price. Preserve custody, chronology, source colour and every actual contribution through preparation, trade and recycling. The complete Tannery's permission to choose different Leather panels remains; grouping equivalent raw parts is not a renewed matching-only crafting restriction.

## 3. A visible Apex needs an explicit label

**Accepted:** Apex status is recognizable beyond lack of movement. Use the actual `WorldEnemy.isApex`/existing Apex authority, never immobility, size, colour, rarity or a guessed species.

Show a clear **Apex** badge with the already displayed creature marker/target name, and repeat it in the existing creature detail/encounter header where that creature is legitimately disclosed. A sessile ordinary creature is not an Apex. “Apex creature” is sufficient when its proper identity is still unknown.

The badge uses the creature's existing permitted visibility/disclosure result, including any already-authorized Apex range rule; it creates no extra fog bypass, hidden enemy marker or off-screen alert. No lingering marker where an enemy is no longer legitimately displayed, and no hidden species name, reward or movement information. Keep Apex's actual encounter/movement rules unchanged. This is a native semantic marker first; Asset gets no speculative artwork assignment before the implemented consumer is named.

## 4. Category controls for optional field notices

**Accepted:** Settings exposes separate monster-notice and mining/gather-result controls. Muting presentation never disables creature behavior, harvesting, resources, knowledge, receipts or necessary decisions.

Current consumers are `SettingsView`/`AppSettings`, `GameStore.WorldFieldEventBatchV1` and `WorldFieldNarration`, the compact/expanded event panes in `WorldView`, and the separate `WorldMiningFeedbackGroupV1`. Inventory of current event families: enemy sight/alert; resource pickups/harvest/early-material hits; portals/caches/travellers/pages/learning/loot/Essence/animal progress; blocked/refused actions, extra-turn ground, damage/poison, full satchel, crumbling/collapse and ejection. This is the relevant existing field feedback, not OS push notifications or a new notification framework.

**Design first-pass grouping/defaults:**

| Settings toggle | Default | Routine events controlled |
| --- | --- | --- |
| Monster notices | On | `enemySighted`, `enemyAlerted` and any equivalent optional, already-disclosed monster popup |
| Mining and gathering results | Off | Routine `pickedUp` resource, `harvested`, `earlyMaterialHit` progress/yield/depletion popups and the mining-result overlay |
| Finds and learning | On | Optional portal/cache/traveller discovery, learned words/patterns/schematics/Gambits, loot/Essence results, animal-attendance/trust/join progress notices |

These defaults are Design tuning, not additional personal approvals attributed to Aimee. Preserve an existing explicit preference if one exists; do not overwrite user choices on launch/update. Persist through the existing app-settings owner, with no new gameplay save/knowledge dependency. The user may change any of these category choices.

**Always preserve:** blocked/refused/failed-save explanations; actual damage and poison; extra-turn ground feedback; satchel-full/Waiting decisions; instability/crumbling/collapse/ejection; combat entry/choices and return summaries; and explicitly requested reading/inspection/use content when the notice is the only result presentation. For example a requested page's prose must not disappear because “Finds and learning” is off. Existing permanent map markers, target details, yields/stock/depletion state and Diary/knowledge remain available. The Apex badge itself is not an optional monster popup.

Classify by typed event/action/disposition, never by matching English words. A single action can have both muted gathering results and an essential hazard; filter individual optional presentations, never suppress the whole action/batch. Keep canonical raw event IDs, commit/disclosure/receipt data and rule execution unchanged. Filter the event panel **and** the separate mining overlay so the setting actually silences duplicate result surfaces. Visible Read-all counts and Dismiss/advance refer to the remaining presented messages, not invisible notices.

A batch with no remaining visible notices produces no empty card or invisible tap target. Turning a category off removes its queued optional presentation; turning it back on affects future notices rather than dumping an old muted queue. Do not reset deadlines, replay rewards or replace actual required interaction with a notification. Keep this a small event-category projection/settings change inside the current owners.
